# Diary-Self：Java 中级工程师项目面试题

> 适用对象：2～3 年 Java 开发经验，目标岗位为 Java 中级工程师  
> 题目构成：30 道项目深度与广度题 + 30 道生产场景题  
> 出题依据：当前仓库的实际代码，而不是通用八股题库

## 一、项目审查摘要

Diary-Self 当前是一个 Maven 多模块项目，使用 Java 21、Spring Boot 3.5.x、Spring Cloud Gateway、Nacos、MySQL、MyBatis/MyBatis-Plus、Redis、RocketMQ、RabbitMQ、OSS、XXL-JOB、Netty/WebSocket、Actuator/Prometheus 等技术。业务模块包括用户、文件、菜谱、饮食、目标、恋爱记录、AI、通知、时光机和系统信息等。

面试时应主动区分三类内容：

1. **已经形成完整链路的实现**：例如 JWT + Redis 会话、AI 异步任务、Transactional Outbox、任务租约与恢复、目标导出策略等。
2. **已经实现但仍存在工程风险的代码**：例如本地 ID 生成器缺少机器位、部分接口仍信任客户端传入的 userId、文件上传跨 DB/OSS/MQ 的一致性、固定窗口限流等。
3. **仍处于 TODO 或骨架状态的能力**：例如通知消费者的用户解析和实际 WebSocket 推送、恋爱记录缓存、恋爱记录 Outbox 等。面试中不能把这类内容描述成已经完整上线。

建议答题方式：先说当前实现，再说为什么这样设计，最后主动指出边界、风险和演进方案。只背定义不能体现中级工程师水平。

**情境**：notify 服务从单实例扩到 10 个实例，用户连接随机分布。

请估算文件描述符、内存、EventLoop、心跳流量，并设计用户到节点的路由注册。业务消息到达任意消费者后，怎样转发到真正持有 Channel 的节点？

**继续追问**：使用粘性会话、Redis Pub/Sub、MQ 分节点队列各有什么优缺点？

**评价点**：连接容量估算、OS 参数、连接注册、跨节点路由、广播风暴避免、优雅下线。

## 场景 21：WebSocket 节点宕机，在线消息与离线消息发生竞态

**情境**：ChannelManager 判断用户在线后节点立刻宕机，消息既没有成功推送，也没有存为离线消息。

如何定义“已送达”：写入 Channel、客户端 ACK，还是业务已读？请设计 messageId、服务端持久化、客户端 ACK、超时重投和去重机制。

**继续追问**：多设备登录时任一设备 ACK 还是所有设备 ACK 才算送达？

**评价点**：在线判断不是交付保证、持久化优先、ACK 层级、至少一次推送与客户端去重。

## 场景 22：两个并发请求为同一用户创建情侣关系

**情境**：两个请求都先查到 count=0，然后都执行 INSERT。

为什么“先查是否存在”不能保证唯一？请在数据库唯一约束、事务隔离、悲观锁、分布式锁中选择方案，并说明对双方关系的约束应如何建模。

**继续追问**：owner=A/partner=B 与 owner=B/partner=A 如何判定为同一关系？

**评价点**：唯一不变量必须由数据库兜底、规范化 pair key、捕获 DuplicateKeyException、避免过度依赖分布式锁。

## 场景 23：攻击者伪造 userId 读取他人的恋爱记录

**情境**：攻击者绕过网关直连 love 服务，或在 DTO 中填写其他人的 ownerUserId/coupleId。

请指出认证、授权和数据归属校验分别应该放在哪里。仅在 Controller 比较 userId 是否足够？Mapper SQL 应怎样将当前用户条件带入每次读写？

**继续追问**：管理员查看用户数据如何避免到处写 if-admin？

**评价点**：纵深防御、不可信任客户端字段、SQL 级资源归属、统一授权策略、审计。

## 场景 24：同一个 refresh token 被并发使用或被盗用

**情境**：正常客户端与攻击者在同一毫秒刷新，二者都通过了“白名单存在”检查。

怎样用 Lua、Redis 事务或单次使用标记完成原子消费？检测到旧 refresh token 再次使用时，是只吊销当前 Token family，还是踢出该用户所有设备？

**继续追问**：用户多端登录时 Token family 应如何建模？

**评价点**：rotation、replay detection、原子 compare-and-delete、设备/会话维度、风险响应。

## 场景 25：多实例出现主键冲突，或机器时钟回拨

**情境**：两个服务实例在同一毫秒生成相同 ID；另一台机器 NTP 调整导致时间倒退。

请先解释当前 `MyUtils` 为什么会冲突，再给出短期止血和长期替代。更换 ID 算法时如何保证新旧 ID 共存、索引性能和前端精度？

**继续追问**：若已发生主键冲突，为什么简单重试可能掩盖 clientRequestId 幂等冲突？

**评价点**：机器位/号段服务、时钟回拨策略、无符号 BIGINT、灰度兼容、冲突类型识别。

## 场景 26：需要不停机修改表结构和消息结构

**情境**：给 ai_task 新增必填字段，并修改 AI 完成事件格式，不能停服。

请给出 Expand–Migrate–Contract 的发布顺序：先加可空列/默认值、代码双读写、回填、约束、删除旧字段。消息 Producer 与 Consumer 的升级顺序是什么？

**继续追问**：大表回填如何限速、断点续跑并避免主从延迟？

**评价点**：向前/向后兼容、分阶段 DDL、批次回填、双写审计、先 Consumer 后 Producer。

## 场景 27：服务扩成多实例后定时任务重复执行

**情境**：每个 AI 实例都会执行 Outbox Publisher、超时恢复和清理任务；每个 XXL-JOB Executor 也可能接到任务。

哪些任务可以依赖数据库 CAS 安全并行，哪些需要分片、领导者选举或分布式锁？锁超时和任务实际执行时间不一致时如何避免双执行？

**继续追问**：为什么“加 Redis 锁”不能代替任务本身的幂等？

**评价点**：可并行扫描 + 行级抢占、调度分片、fencing、幂等优先、锁只是减少竞争。

## 场景 28：机房故障，需要恢复 Diary-Self

**情境**：MySQL、Redis、MQ 和 OSS 跨多个系统，业务提出 RPO 5 分钟、RTO 30 分钟。

请制定备份、binlog/PITR、跨可用区复制、Redis 持久化、MQ 副本、OSS 版本/跨区域复制与恢复演练方案。恢复顺序为何重要？

**继续追问**：MySQL 恢复到 T1、MQ 恢复到 T2，会造成哪些事件错位？怎样通过 Outbox 和对账修复？

**评价点**：明确 RPO/RTO、跨系统时间点一致性、恢复演练、Outbox 重放、业务对账。

## 场景 29：生产环境 P99 延迟突然升高，但错误率不高

**情境**：用户反馈“偶尔很慢”，平均延迟正常，P99 从 300 ms 升到 8 s。

请说明你会查看哪些网关、JVM、线程池、GC、连接池、MySQL、Redis、MQ 和外部调用指标。如何利用 traceId 把一次慢请求串起来？

**继续追问**：日志量太大时怎样采样，同时保留错误和慢请求？如何建立 SLI/SLO 与告警阈值？

**评价点**：关注分位数而非平均值、RED/USE、火焰图/线程 dump、分布式追踪、基于 SLO 告警。

## 场景 30：一次版本发布后故障率上升，需要快速回滚

**情境**：新版本同时修改应用代码、数据库字段和消息格式，灰度实例错误率快速升高。

请设计 CI/CD 流水线、自动化测试、制品不可变、灰度/金丝雀、指标门禁、功能开关和一键回滚。若数据库迁移已执行且新消息已发出，为什么“回滚 Jar”可能不够？

**继续追问**：如何提前验证旧版本能否读取新版本写入的数据与消息？

**评价点**：向后兼容发布、可逆迁移、契约测试、灰度观测、Feature Flag、回滚与前滚预案。

# 第三部分：建议的面试使用方式

每道项目题建议回答 3～5 分钟，每道场景题建议回答 5～8 分钟。场景题可以统一采用下面的结构：

1. **先确认目标与现状**：流量、数据量、SLA、错误比例、是否允许降级。
2. **用证据定位瓶颈**：指标、日志、Trace、线程 dump、慢 SQL、MQ lag，而不是直接猜结论。
3. **给出短期止血方案**：限流、降级、摘流量、扩容、关闭高风险功能。
4. **给出长期治理方案**：架构改造、幂等、补偿、容量规划、测试和演练。
5. **说明副作用与验证方法**：任何优化都应说明成本、风险、回滚和验证指标。

中级工程师回答的关键不在于堆砌组件，而在于能够明确：当前实现保证了什么、没有保证什么；故障窗口在哪里；怎样用数据库约束、状态机、幂等、监控和补偿把系统做成可恢复的工程系统。
