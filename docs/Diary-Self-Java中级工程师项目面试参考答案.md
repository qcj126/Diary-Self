# Diary-Self：Java 中级工程师项目面试参考答案

> 本文与《Diary-Self-Java中级工程师项目面试题（30道深度题+30道场景题）》逐题对应。  
> 答案定位：2～3 年经验的 Java 中级工程师，不要求逐字背诵，应结合自己的实际开发经历重新组织语言。

## 答题原则

一个有说服力的项目回答通常包含四层：

1. **事实层**：当前项目实际怎么做。
2. **原理层**：为什么这样做，底层机制是什么。
3. **边界层**：当前方案不能保证什么，故障窗口在哪里。
4. **演进层**：数据量、并发量或可用性要求提高后怎样改。

面试中不要把 TODO、注释代码或只有框架的模块说成已经生产落地。例如通知模块已经搭建 Netty Pipeline、ChannelManager 和 RabbitMQ Consumer，但消费者的用户提取和真实推送仍未闭环，应该如实说明。

# 第一部分：30 道项目深度题参考答案

## 1. Diary-Self 的模块拆分

Diary-Self 按业务能力拆成 user、file、recipe、goal、love、AI、notify 等模块。这样做的收益是业务职责更清晰，并且 AI、文件、通知这类资源模型差异较大的服务可以独立扩容和故障隔离。例如 AI 服务受第三方模型并发限制，文件服务受网络和 OSS I/O 限制，两者不应该共享同一个线程池和扩容策略。

但当前拆分也有成本。项目规模和测试体系尚不足以完全抵消微服务带来的配置、部署、链路追踪、数据一致性和运维复杂度。`diary-common` 同时承载大量实体、DTO、枚举和异常，`diary-config` 又被多个服务直接依赖，容易形成共享内核过大、一次公共改动迫使多个服务一起升级的问题。

更稳妥的边界是：

- common 只保留稳定的跨服务协议、少量基础类型和事件信封，业务数据库实体尽量由拥有该数据的服务管理。
- 公共配置拆成按能力启用的 starter，例如 redis-starter、oss-starter、observability-starter，通过条件注解装配。
- 服务之间通过 API 或事件协作，不直接跨库查询对方的表。
- 如果团队和流量较小，可先采用模块化单体，保留清晰边界；只有存在独立扩容、隔离或发布需求时再物理拆分。

是否拆成微服务不是看用了多少组件，而是看业务边界、团队自治、独立发布和故障隔离的收益能否覆盖分布式复杂度。

## 2. 受保护请求的完整调用链

客户端在 Authorization 中携带 access token。Gateway 的 `JwtAuthFilter` 先跳过 OPTIONS 和白名单路径，然后验证 Bearer 格式、JWT 签名、过期时间和 token_type。之后从 JWT 读取 username、userId、roles、jti，再使用 Reactive Redis 同时检查白名单存在、黑名单不存在。管理员路径还会校验 admin 角色。

校验通过后，网关先删除客户端自己携带的 `X-Auth-*` 头，再写入可信的 userId、username 和 roles。Gateway 通过 Nacos 服务发现和负载均衡将请求转给业务服务。Servlet 业务服务中的 `CurrentUser` 从可信头读取 userId，Service/Mapper 查询时还应把 userId 放进资源归属条件。

Gateway 使用 WebFlux，少量 EventLoop 线程处理大量连接，所以 Redis 必须用响应式客户端，不能在过滤器中调用 JDBC或阻塞式 Redis。业务服务使用 Spring MVC、MyBatis 和 JDBC，本身是阻塞模型，由 Tomcat 工作线程承载。因此整个系统不是端到端响应式，只是网关层响应式。

合理的链路还应在网关生成或接收 traceId，经 HTTP 头传播；创建 MQ 事件时写入 traceId，Consumer 收到后恢复到 MDC。401 表示未认证或 Token 无效，403 表示身份有效但权限不足。

## 3. JWT 与 Redis 会话

纯 JWT 的优点是验证只依赖签名，性能和可用性高；缺点是签发后在过期前难以立即撤销。项目使用 JWT + Redis：JWT 承载身份和角色，Redis 白名单表示当前会话仍有效，黑名单用于记录已撤销 jti，用户 Token 索引用于踢出某个用户的全部会话。

access token 应较短，refresh token 较长。刷新时旧 access 和 refresh 都要失效，再签发一对新 Token，这叫 refresh token rotation，可缩短被盗 Token 的可利用时间。当前实现的“检查白名单—加入黑名单—删除白名单—签发新 Token”是多条命令，并发刷新时存在两个请求都通过前置检查的竞态。可用 Lua 脚本将“校验旧 jti、标记已消费、删除旧值”做成原子操作，并用 Token family 记录一次会话的轮换链。已经消费过的 refresh token 再出现时，应视为重放攻击并吊销该 family。

Redis 故障时，鉴权通常安全优先，管理和写接口 fail-closed。若业务允许，可对低风险只读接口使用秒级本地正缓存，但会扩大踢人后的有效窗口，必须明确风险。Redis 本身应部署 Sentinel/Cluster，并设置很短的连接和命令超时，避免网关线程长期等待。

## 4. 身份头的安全边界

网关删除客户端伪造的身份头再重写，可以防止正常从网关进入的请求伪造 userId。但 `CurrentUser` 只读取头部，如果业务服务端口可被直接访问，攻击者仍可绕过网关自己构造该头。因此身份头只在“网络上保证业务服务只能被网关访问”的前提下可信。

应采用纵深防御：

- 网络层只暴露网关，业务端口放在私网或由安全组、Kubernetes NetworkPolicy 限制。
- 服务层可再次校验 JWT，或使用网关到服务的 mTLS、短期内部签名头，防止伪造调用。
- 资源层绝不能相信 DTO 中的 ownerUserId、creatorUserId。它们应该来自 `CurrentUser`，查询和更新 SQL 必须带 `currentUserId` 或基于 couple membership 的 EXISTS 条件。
- 管理员越权访问应走统一授权策略并留下审计，而不是在各方法散落 `if admin`。

认证回答“你是谁”，授权回答“你能做什么”，数据归属校验回答“这条记录是否属于你”。三层缺一不可。

## 5. Gateway 与 MVC 的线程模型

WebFlux 基于事件循环，线程不与请求一一绑定。异步网络操作完成后通过回调继续执行，因此适合大量并发 I/O，但前提是整个调用链不能阻塞。若在 Netty EventLoop 中执行 JDBC、`Thread.sleep` 或阻塞 Redis，少数线程会被占满，其他连接即使没有高 CPU 也会排队。

Spring MVC 通常一个请求占用一个 Tomcat 工作线程，MyBatis/JDBC 调用期间线程阻塞。它的模型简单，适合当前大量 JDBC 业务。把 JDBC 包一层 `Mono` 不会让驱动变成非阻塞，只是把阻塞工作转移到另一个线程池，还会增加调度和上下文切换。

EventLoop 数量通常与 CPU 核心相关；Tomcat 线程数需要结合请求延迟、CPU、连接池和下游容量测算。即使 Tomcat 有 500 个线程，Hikari 只有 30 个连接，数据库请求仍会在连接池等待。Reactor 背压也不能自动控制 MySQL，必须通过连接池、并发限制和超时形成明确边界。

只有在驱动、缓存、HTTP 客户端和业务链路都能非阻塞，并且高连接并发确有收益时，才值得把某服务端到端响应式化。

## 6. Spring Bean 扫描与公共配置

`@SpringBootApplication` 默认扫描启动类所在包及子包。Maven 依赖只表示类在 classpath 中，并不表示那些包一定会被扫描。项目部分启动类显式扫描 `diary.common`、`diary.config`、`diary.utils`，所以公共的 ControllerAdvice、Redis、线程池、MQ 或 OSS 配置可能一起进入容器。

风险是某服务只需要一个工具类，却因为宽泛扫描创建 RabbitMQ 或 OSS Bean；对应配置不存在时服务甚至无法启动。多个服务还可能出现相同 Bean 名、序列化方式或 ObjectMapper 配置互相覆盖。

更规范的方式是将公共能力做成 Spring Boot 自动配置：

- 用 `@AutoConfiguration` 和 imports 注册，而不是要求业务扩大扫描范围。
- 用 `@ConditionalOnClass`、`@ConditionalOnProperty`、`@ConditionalOnMissingBean` 控制启用条件。
- 按功能拆 starter，业务只引入真正需要的依赖。
- 对外暴露 `@ConfigurationProperties` 并在启动时校验。

这样可以让依赖关系、启用条件和默认行为更明确，也降低公共模块改动的爆炸半径。

## 7. `@Transactional` 的保证范围

Spring 事务通常由代理拦截 public 方法，在进入方法前从连接池获取连接并绑定到当前线程，正常返回时提交，符合回滚规则的异常抛出时回滚。`rollbackFor = Exception.class` 让受检异常也回滚。

`DiaryLoveAddServiceImpl#addRecord` 的多张表写入可在同一个 MySQL 事务中原子提交；`createTaskAndOutbox` 把任务和 Outbox 同时写入，也由同一本地事务保证“不可能只成功一张表”。但事务不能回滚已上传到 OSS 的对象、已经发到 MQ 的消息或已经调用的 AI。

常见陷阱包括：

- 同类内部 `this.method()` 不经过代理，目标方法上的事务可能不生效。
- 捕获异常后吞掉，代理看到正常返回就会提交。
- 在事务内执行长耗时 HTTP、AI、OSS 调用，会长时间占用数据库连接和锁。
- `REQUIRES_NEW` 可用于独立记录失败，但会让内外事务分别提交；若业务要求两者原子一致，就不能滥用。

因此正确做法通常是缩短本地事务，将跨系统动作改成 Outbox、状态机和补偿，而不是追求一个覆盖所有资源的“大事务”。

## 8. 恋爱记录聚合写入

新增记录同时影响地点、主记录、图片关系、标签和心情关系，这些数据共同维护“记录必须完整”的业务不变量，因此适合在一个本地事务内提交。一般先验证所有输入和归属，再准备 ID，随后写主表和关系表。数据库应通过非空、唯一、检查约束和必要的外键兜底，Java 校验则提供更友好的错误和跨字段规则。

只判断每个 Mapper 返回值大于 0 并不充分：空图片或空标签可能生成非法批量 SQL；批量影响行数也未必等于输入数量；重复关系可能因唯一约束只插入部分或直接异常。因此要先显式处理空列表，并校验影响行数是否等于预期数量，异常应继续抛出以触发回滚。

安全上还必须校验 coupleId 当前用户确实是成员、imageId 属于当前用户且状态为 SUCCESS、locationId 属于同一 couple。不能因为 ID 存在就允许关联。

如果未来聚合过大，可把核心记录与必要关系保持强一致，把统计、时间线索引、相册重建等派生数据通过事务提交后的领域事件异步更新。

## 9. MyBatis 动态 SQL

`#{}` 会生成预编译参数，占位值与 SQL 结构分离，能防止大部分 SQL 注入；`${}` 是字符串直接拼接，只能用于经过严格白名单校验的列名、排序方向等结构部分。动态 `<if>` 能减少无关条件，但不同 SQL 形状可能产生不同执行计划，必须用真实参数检查。

`LIKE '%关键词%'` 左侧通配符使普通 B+Tree 无法从有序前缀定位，数据大后通常全表或大范围扫描。小规模可接受；规模增大后可使用前缀搜索、MySQL FULLTEXT，或将搜索交给 Elasticsearch/OpenSearch，并明确索引同步的一致性。

大 IN 会导致 SQL 很长、解析成本高和计划不稳定，可分批、使用临时表或重新设计查询。MyBatis 一级缓存是 SqlSession 级，二级缓存是 namespace 级；在分布式服务和频繁更新场景中二级缓存失效治理困难，通常更倾向显式 Redis/本地缓存。

Mapper XML 属性名错误往往在运行到该语句时才暴露，因此应为关键 Mapper 编写使用真实 MySQL 的集成测试，并在 CI 中执行迁移和查询，而不能只靠编译。

## 10. 索引与游标分页

时间线核心过滤是 coupleId、deleted，排序是 `record_date DESC, sort ASC, id DESC`。现有 `(couple_id, deleted, record_date DESC, id DESC)` 能帮助按情侣和日期定位，但中间缺少 sort，数据库可能仍需额外排序。候选索引可按实际查询频率设计为 `(couple_id, deleted, record_date DESC, sort ASC, id DESC)`，但是否采用必须通过 EXPLAIN 和写入成本验证。

深分页 `LIMIT 1000000, 20` 仍需扫描并丢弃前一百万行。游标分页记录上一页最后一条的 `(recordDate, sort, id)`，下一页使用与排序一致的字典序条件。例如日期更早，或日期相同且 sort 更大，或日期和 sort 相同且 id 更小。实际 SQL 可写成 OR 条件，也可利用数据库支持的行值比较，但混合升降序时要谨慎验证。

id 是最终稳定的唯一排序键，因此即使多条记录日期和 sort 相同，也不会重复或遗漏。覆盖索引表示查询需要的列都在索引中，无需回表；记录内容较大，不适合全塞进索引，通常先从索引取 ID 再回表是合理权衡。

## 11. 逻辑删除

逻辑删除保留数据，便于审计和恢复，也避免立刻破坏历史引用；代价是每个查询都必须带 `deleted=0`，表和索引持续膨胀，唯一约束也更复杂。若唯一键不包含删除状态，删除后可能无法创建同名数据；简单把 deleted 放进唯一键，又可能因为多次删除值相同而冲突，常用做法是删除时改写业务唯一字段、使用删除时间/唯一删除标识，或把历史数据归档到另一张表。

主记录逻辑删除而关系表保留时，统计查询必须通过主表过滤，否则会把已删除记录的图片、标签和心情算进去。还要定义恢复时关联数据是否全部恢复、OSS 对象是否仍保留。

缓存方面，删除事务提交前就删缓存可能发生事务回滚而缓存已丢；提交后删缓存更合适，可用事务同步回调或事务 Outbox。Cache Aside 仍存在并发旧值回填窗口，可用版本号 key、延迟双删或短 TTL 降低影响。

是否逻辑删除取决于审计与恢复需求；临时关系、可重建缓存和过期中间数据通常更适合物理删除或归档。

## 12. 自研 ID 生成器

当前算法在单 JVM 内通过 `synchronized` 保证同一毫秒的 sequence 唯一，最多 4096 个；超过后自旋等待下一毫秒。问题在于高 22 位预留了空间，却没有编码 workerId 或 dataCenterId。两个 JVM 在同一毫秒从 sequence=0 开始，会生成相同 ID，所以它不适合多实例微服务。

时钟回拨时当前实现直接抛异常，可能导致整个写链路不可用。短期可为不同实例配置不重复的 workerId 并把机器位写入 ID；容器环境要通过集中分配、数据库租约或 StatefulSet 序号保证稳定且不冲突。长期更建议使用成熟 Snowflake 实现、Leaf/号段服务或数据库号段表，并监控时钟偏移。

数据库自增简单且索引友好，但跨库和提前生成困难；UUID 无中心依赖但普通随机 UUID 索引局部性差、体积大；号段吞吐高且较能容忍时间问题；Snowflake 有序、无数据库依赖，但必须治理机器号和时钟。

BIGINT 返回前端时还要以字符串表示，因为 JavaScript Number 无法精确表示全部 64 位整数。项目用户登录已经意识到这一点，其他 ID 接口也应统一。

## 13. AI 异步任务 API

AI 调用是秒级甚至分钟级长任务，同步等待会占用 HTTP 连接和 Web 线程，且容易超过网关、客户端和代理超时。项目将提交建模为异步任务：POST 返回 202 Accepted 和 Location，客户端通过状态与结果接口查询。这样 HTTP 请求只负责可靠接收，执行吞吐由 MQ Consumer 和模型并发控制。

客户端应把 PENDING 理解为任务已落库但尚未确认进入 Broker，QUEUED 是已排队，RUNNING 是执行中，RETRY_WAIT 是等待重试，SUCCESS/FAILED/CANCELLED/DEAD_LETTER 是终态。未完成的结果接口返回 202 是合理的；任务不存在或不属于当前用户应返回 404，避免泄露资源存在性。

后续可以增加取消接口，但取消只能在未开始时立即生效；正在调用外部模型时要看上游是否支持取消，并用状态 CAS 防止取消与成功互相覆盖。进度可以是粗粒度步骤而不是虚假的百分比。WebSocket/SSE 只用于加速通知，状态仍应以持久化任务表为事实来源。

任务和结果需要定义保留期，终态历史可归档；含敏感输入的 snapshot 还要加密、脱敏和按合规要求删除。

## 14. AI 接口幂等

先查询再插入存在 TOCTOU 竞态：两个请求都可能查询不到，然后同时插入。数据库 `(user_id, client_request_id)` 联合唯一约束是最终权威。后插入者收到 DuplicateKeyException 后回查已有任务并返回，才能正确处理并发。

仅凭 clientRequestId 返回旧任务不够，因为客户端可能错误地复用 key 提交不同参数。项目把请求转成稳定的规范形式，materials 使用有序 Map，再做 SHA-256；相同 key 但不同 hash 返回 409，防止悄悄复用错误结果。

规范化要明确语义：字符串是否 trim、flag 是否大写、空字段与缺省字段是否等价、数字 1 与 1.0 是否等价。否则语义相同的请求可能得到不同指纹，或语义不同的请求意外相同。哈希的作用主要是固定长度比较和防误用，不是安全签名。

幂等记录是否过期取决于业务。如果允许一段时间后重新分析，可让客户端使用新的 clientRequestId，或定义幂等窗口；不要删除唯一约束后悄悄改变旧 key 的语义。存量 requestHash 回填使用 CAS 并发更新是合理做法。

## 15. Transactional Outbox

直接执行“先写业务表，再发 MQ”时，DB 成功、MQ 失败会丢事件；先发 MQ、再写 DB 则可能让消费者看到不存在的业务数据。Outbox 将业务记录和待发送事件写入同一个本地数据库事务，只要事务提交，Publisher 最终就可以扫描并发送；事务回滚则两者都不存在。

它保证的是发送意图与业务数据的本地原子性，不保证消息只发送一次。Broker 收到消息后，Publisher 可能在标记 SENT 前崩溃，恢复后会再次发送。因此端到端语义仍是 At-Least-Once，Consumer 必须以 eventId、taskId 或业务唯一键幂等。

Publisher 永久停止时事件不会丢，但会一直积压，所以要部署多个实例、用 CAS 抢占、监控积压数量和最老事件年龄。Outbox 必须和业务表同一个事务资源；放在另一个数据库又回到了分布式双写。

定时轮询实现简单、容易控制，但有扫描延迟和数据库压力。CDC/Debezium 从 binlog 捕获 Outbox 变更，延迟低且减少轮询，但引入连接器、offset 和运维复杂度。二者都不能免除消费幂等、死信和对账。

## 16. Outbox 状态机与乐观锁

多个实例可以同时查询到 NEW 或 RETRY_WAIT 行，但 `claimOutbox` 的 UPDATE 同时限制 id、旧 versionId 和合法前置状态。第一个实例更新成功后状态变为 SENDING、版本加一，其他实例仍带旧版本，影响行数为 0，所以只有一个发送者获得处理权。这是数据库 CAS，不要求长时间持有行锁。

发送后标记 SENT 同样必须带 SENDING 和新版本。调用方 claim 成功后把内存对象的 versionId 加一，是为了后续 UPDATE 与数据库版本一致。若应用在 Broker 接收成功后崩溃，数据库仍是 SENDING；超时只能说明结果未知，不能判断消息未发送，所以恢复到重试会产生重复消息。这正是 Consumer 必须幂等的原因。

另一种实现是事务中使用 `FOR UPDATE SKIP LOCKED` 批量取任务，适合数据库支持且扫描事务很短的场景；当前逐行 CAS 不会长时间占锁，但会多一些往返和抢占失败。

SENT 记录在超过审计和排障窗口后可分批删除，避免大事务和锁；DEAD 代表自动发送已经耗尽，必须保留、告警并支持人工重放。人工重放最好创建新的 Outbox 记录并关联原 eventId，而不是直接篡改旧记录。

## 17. AI 任务状态机

主要合法迁移是：PENDING → QUEUED → RUNNING → SUCCESS；执行失败但可重试时 RUNNING → RETRY_WAIT → QUEUED/RUNNING；永久失败或次数耗尽进入 FAILED；投递 Outbox 耗尽且尚未执行进入 DEAD_LETTER；取消则进入 CANCELLED。终态不应再被普通消息改回运行态。

项目没有提供“任意设置 status”的通用 SQL，而是为 claim、成功、失败、恢复等动作分别写条件 UPDATE。这样数据库会同时校验前置状态、workerId、versionId 和 attemptCount，即使旧 Worker、重复消息和恢复任务并发执行，也不能随意覆盖。

允许 PENDING 直接 claim 是为处理一个真实竞态：消息已进入 Broker，但 Publisher 尚未来得及把任务状态更新为 QUEUED，Consumer 已经收到消息。若只允许 QUEUED，会错误拒绝一条有效消息。

attemptCount 在成功抢占执行权时增加更准确，因为它表示真实开始了一次尝试；若只在异常时加，进程崩溃这种没有异常回调的尝试就不会计数。终态应不可逆，人工重放应创建新的 attempt/run 或新任务，保留原失败记录用于审计。

## 18. 租约、续租与 fencing

租约是带过期时间的所有权，不是假设持有者永远存活的锁。Worker claim 后写 workerId、leaseUntil 并增加 versionId；长模型调用期间按约三分之一租约周期续租。这样单次续租失败还有后续机会，也留出了网络抖动和调度延迟空间。

如果旧 Worker 停顿导致租约过期，新 Worker 可以接管并获得新的 workerId/version。旧 Worker 恢复后即使拿到模型结果，`markSuccessIfOwned` 必须同时匹配 RUNNING、旧 workerId 和旧 versionId，因此更新 0 行，无法覆盖新 Worker。这一版本就是 fencing token，解决“锁过期但旧持有者还在工作”的问题。

租约过期判断使用数据库当前时间，避免多实例应用时钟差导致不同判断。单线程续租器在任务很多或数据库慢时可能延迟所有续租，应监控调度延迟；可使用合适大小的 ScheduledThreadPool、批量续租或时间轮，但仍要限制同时运行任务数。

仅用 Redis 锁也不够，因为锁过期后旧线程不会自动停止。任何最终写入资源都需要识别更新者世代，才能真正隔离迟到的旧持有者。

## 19. RocketMQ 重复消费

Consumer 首先对任务执行原子 claim。两个实例同时收到重复消息时，只有一个能把 QUEUED/PENDING/RETRY_WAIT 改为 RUNNING；另一个 claim 失败后读取当前任务。若已是终态直接返回 SUCCESS ACK，若是另一个 Worker 持有有效租约也 ACK 当前重复副本。租约过期后才允许重新抢占。

这能避免大部分重复模型调用，但不能宣称 Exactly Once。模型调用是外部副作用：若模型已完成而本地结果事务尚未提交时进程崩溃，数据库看不到结果，后续 Worker 会再次调用模型。数据库唯一约束可阻止重复结果行，却不能退回已经产生的模型费用。

如果第三方支持幂等键，应传稳定的 taskId 或 clientRequestId + 业务版本；如果支持查询历史结果，可在重试前查询。否则只能通过合理租约、结果步骤持久化、较少的自动重试和成本告警降低重复概率。

ACK 的含义只是该消息副本不再重投，不代表整个业务天然只执行一次。消费幂等应由状态机、唯一约束、CAS 和外部幂等共同完成。

## 20. 失败分类与重试

参数非法、快照无法反序列化、业务类型不支持通常是永久错误，重试不会改变结果，应立即 FAILED。网络超时、模型 429/5xx、数据库短暂不可用通常可重试，但要根据错误码和幂等性判断。代码 NPE 可能是 Bug，盲目重试会形成毒消息，应有限次数后死信并告警。

重试必须有上限，否则一个永久故障会无限消耗线程、MQ 和上游配额。指数退避给依赖恢复时间，jitter 让大量失败任务不要在同一时刻再次请求，避免惊群。还应有全局 retry budget：当系统整体失败时，重试流量不能超过正常流量的一定比例。

业务 FAILED 表示任务语义已失败；MQ DLQ 表示某条消息经过 Broker 策略仍无法成功消费，两者不是一回事。Outbox DEAD 表示事件未能可靠发送，也与 Consumer DLQ 不同。三种状态都需要可检索的错误码、原始上下文、告警和人工处理入口。

人工重放应保留原记录，新建一次带操作人、原因和新 eventId 的重放记录，继续用原业务幂等键约束副作用。

## 21. Redis Lua 限流

当前以 `epochMinute` 组成 key，在一分钟内执行 INCR，第一次设置 EXPIRE，因此是固定窗口计数器。Lua 在 Redis 单线程内原子执行，避免 INCR 成功但 EXPIRE 未设置形成永久 key，也避免两个第一次请求竞态。

固定窗口的问题是边界突刺：用户可在上一分钟最后几秒用完配额，又在下一分钟开始立即用满，短时间内达到约两倍限制。滑动窗口日志可用 ZSET 保存请求时间，精确但空间和操作成本高；滑动计数器用相邻窗口加权；令牌桶适合允许一定突发但限制长期速率；漏桶更强调匀速处理。

限流需要分层：用户级防滥用，租户级做公平性，模型级保护供应商配额，实例本地并发保护线程和连接，系统总量保护数据库与 MQ。响应应返回 429，并可带 Retry-After、限额和剩余量。

当前 Redis 异常时返回 false，是 fail-closed，能保护昂贵 AI 资源但降低可用性。也可使用保守的本地令牌桶作短时降级，但必须接受多实例总额度不精确，并设置很小的上限。

## 22. 本地 Semaphore 与集群并发

本地限制 2、部署 10 个实例时，理论集群并发是 20，不会自动保持 2。如果第三方模型全局只允许 8，可通过 Redis/Redisson 分布式信号量、集中式令牌服务，或直接按供应商配额控制 Consumer 总实例和每实例并发。分布式许可还需要租约与崩溃回收。

整个链路的并发必须对齐：MQ 消费线程先拉取很多消息，但本地只有两个许可时，其余消息会失败重投，形成无效流量；数据库连接池过小又会让 claim 和提交排队；模型连接池也可能成为上限。拿不到许可时直接 FAILURE 容易造成重试风暴，更好的方式是限制 Consumer 拉取并发/prefetch、暂停消费，或者发送延迟重试消息。

本地 Semaphore 仍有价值，它能快速保护单实例的线程、内存和连接，不依赖远程组件。实际方案通常是“全局额度 + 本地上限 + MQ 背压”三层组合，并通过队列等待时间、运行并发、429、permit wait time 来调参。

## 23. RocketMQ 与 RabbitMQ 共存

AI 使用 RocketMQ，文件与通知使用 RabbitMQ，可能是历史演进和场景选择的结果。RocketMQ 更常用于高吞吐业务事件、延迟消息和大规模消费；RabbitMQ 路由模型灵活、Confirm/ACK/DLX 生态成熟，适合文件状态通知等。是否统一不能只看技术偏好，还要评估迁移风险、运维成本、团队经验和现有可靠性。

两套 MQ 会带来两套集群、监控、权限、消息语义和故障手册，规模不大时统一可能降低成本。但如果现有链路稳定且迁移收益很小，不应为了“技术栈整齐”冒险。

无论是否统一，都应统一应用层事件信封：eventId、eventType、aggregateId、schemaVersion、occurTime、traceId、producer 等。ACK、重试和 DLQ 仍按各 Broker 语义实现，不能封装到让开发者误以为完全一致。

迁移时可先让 Producer 通过 Outbox 双发，新 Consumer 影子消费并对账，再切换读取和停止旧链路。双发期间必须用同一业务 eventId 去重，并保留快速回退能力。

## 24. 文件上传跨系统一致性

当前过程是：数据库插入 PROCESSING，复制请求文件到临时目录，异步上传 OSS，发送 RabbitMQ，Consumer 更新 SUCCESS。故障窗口包括：DB 成功但异步任务未运行；临时文件复制一半；OSS 成功但 MQ 失败；消息成功但 DB 更新失败；DB 成功但 ACK 前断连导致重复消费。

因此会产生数据库孤儿（PROCESSING/FAILED 但无 OSS 对象）和 OSS 孤儿（对象存在但 DB 无有效引用）。本地事务无法覆盖文件系统、OSS 和 RabbitMQ。

改进方式是把文件状态做成明确状态机，上传完成后将“对象已存在 + 待发事件”在数据库事务中更新，配合文件 Outbox；定时扫描超时 PROCESSING 并通过 OSS HEAD 校验 objectKey、size、ETag 后补发或失败。Consumer 只允许 PROCESSING → SUCCESS，重复消息更新应幂等。XXL-JOB 定期双向对账并延迟清理孤儿。

大文件更适合客户端通过 STS 临时凭证或预签名地址直传 OSS，服务端只创建上传会话并在回调/客户端确认时验签和校验对象。这样减少服务带宽、磁盘和线程占用，但权限范围、回调伪造和未确认对象清理必须治理。

## 25. `@Async` 与线程池

ThreadPoolExecutor 的典型执行顺序是：先创建到 corePoolSize，再进入队列；队列满后才扩到 maxPoolSize；队列和最大线程都满后执行拒绝策略。因此大队列会让 maxPoolSize 很少生效，同时增加排队时间和内存占用。

上传线程池未显式拒绝策略时通常使用 AbortPolicy，任务满后抛 `TaskRejectedException`；下载池使用 CallerRunsPolicy，会让提交任务的 Web 线程自己执行下载，形成自然背压，但也可能把 HTTP 请求阻塞数分钟，应结合接口语义决定。

`@Async` 基于代理，同类内部调用可能不生效。void 异步方法的异常无法返回调用方，需要配置 `AsyncUncaughtExceptionHandler`、落库任务状态并告警；只写日志会让业务以为已受理但任务永久丢失。返回 `CompletableFuture` 可以传递结果，但长任务仍应持久化成任务而不是只存在内存 Future。

MultipartFile 可能依赖请求临时文件，请求结束后资源会被容器清理。当前先复制到自有临时文件再异步处理解决了生命周期问题，但必须设置目录配额、清理失败兜底和磁盘监控。

## 26. RabbitMQ ACK 与死信

手动 ACK 表示应用确认业务处理成功；NACK/Reject 可选择 requeue。prefetch=10 限制每个消费者尚未确认的消息数。业务队列绑定 DLX 后，拒绝且不 requeue、消息过期或队列超长的消息会进入死信路由。

当前消费失败直接 `basicNack(..., false, false)`，所以第一次失败就进入 DLQ，并没有实现注释所说的“超过重试次数”。有限重试可以使用一组带 TTL 的重试队列，消息失败后增加 retry-count 并路由到对应延迟队列，过期后回业务队列；超过上限再进最终 DLQ。也可使用 RabbitMQ delayed message 插件。

DB 更新成功但 ACK 前连接断开时消息会再次投递，所以 `updateImageStatusById` 要按 id 和合法前置状态做幂等；如果已 SUCCESS，重复消息应 ACK，而不是当成失败送死信。

Producer Confirm 只说明 Broker 接收到了交换机阶段的消息；Returns 回调处理无法路由到队列；二者都不表示 Consumer 业务成功。真正的端到端可靠性还需要持久化发送意图、消费幂等、DLQ 和对账。

## 27. 图片签名 URL 缓存

签名 URL 自带过期时间，Redis TTL 必须比它短并留安全余量。例如 URL 有效 5 分钟，缓存 4 分钟左右，避免从缓存取到即将或已经失效的地址。若项目工具中的“10”单位不明确，还要确认 Redis 封装到底按秒还是分钟。

当前按 imageId 循环，会产生 N 次 Redis GET；未命中又产生 N 次 DB 查询和签名调用，是典型 N+1。应先 MGET，一次收集未命中 ID，再用 `WHERE id IN (...) AND user_id=?` 批量查 objectKey，批量生成签名并 MSET/流水线写缓存，最后按输入顺序组装。

不存在的 ID 可短时间缓存空标记并配合参数和用户归属校验，减少穿透。热门 key 过期可用互斥重建、逻辑过期或 singleflight，TTL 加随机抖动。私有图片不宜只按 imageId 缓存而忽略访问者权限；要么 URL 本身只能访问该对象且查询前已经授权，要么缓存 key 带权限维度。

删除对象后旧签名在过期前可能仍可访问。高安全场景可使用 CDN 鉴权、缩短 URL 有效期、版本化 objectKey 或对象 ACL 撤销。

## 28. Netty/WebSocket 通知服务

BossGroup 接收连接并注册到 WorkerGroup；Worker EventLoop 负责连接上的 I/O 事件。Pipeline 依次处理 HTTP 编解码、聚合、WebSocket 升级、压缩、空闲检测、JWT 认证、心跳、业务编解码和消息处理。ChannelManager 维护用户与连接关系，离线管理器负责没有在线连接时持久化消息。

EventLoop 线程不能执行阻塞 DB/Redis 操作，否则该线程绑定的多个 Channel 都会停顿。阻塞任务要提交到独立有界业务线程池，完成后再安全地写回 Channel。多端登录通常应建模为 userId → deviceId/channel 集合，而不是一个用户只保存最后一个 Channel。

当前 `NotifyMessageConsumer#extractUserId` 返回 null，`pushToUser` 只打印日志，所以正确表述应是：“已完成 Netty 服务和通知消费的骨架，真实用户解析、Channel 写入、客户端 ACK 和离线闭环尚未完成。”这比把 TODO 说成上线成果更可信。

集群化后需要 userId/deviceId → nodeId 的带 TTL 注册。消息到达任一节点时可按 nodeId 定向转发，或让每个节点消费自己的队列。节点崩溃时注册自动过期，持久化消息仍可重新投递。

## 29. 导出策略与工厂

`Exporter` 定义统一行为，Excel、PDF、Image 分别实现，业务服务只按 exportType 获取策略，新增格式无需修改大量 if/else，符合开闭原则。Spring 自动注入全部实现，`@PostConstruct` 建立 code → instance 映射，查询复杂度是 O(1)。

初始化时若两个实现返回相同 code，当前 `put` 会静默覆盖，应该检测重复并让应用启动失败。初始化结束后映射只读，普通不可变 Map 就够了，`ConcurrentHashMap` 并非必需；如果支持运行时插件注册才需要并发更新。

当前所有导出先写 `ByteArrayOutputStream`，多个目标还在内存中压缩，大批量时可能 OOM。小规模通过 exportSize≤100 限制是一种保护；规模增大后应使用流式响应、SXSSFWorkbook 临时文件、分段生成，或将导出变成异步任务，结果上传 OSS，返回下载链接并设置保留期。

异步导出同样需要任务状态、幂等、用户归属、文件清理、最大数据量和资源隔离，避免导出线程拖垮普通请求。

## 30. 可测试性与可观测性

当前生产代码规模较大，而自动化测试很少，优先级应放在高风险不变量而不是追求覆盖率数字：AI 状态机的重复消息和旧 Worker、Outbox 并发抢占和未知发送结果、Token 轮换和资源归属、文件三方一致性，以及关键 Mapper SQL。

纯函数、参数校验、请求指纹和策略选择适合 JUnit/Mockito；事务、SQL、Redis Lua、Broker ACK 必须使用 Testcontainers 或集成环境。MQ 事件还需要生产者/消费者契约测试。关键链路应做并发测试和故障注入。

可观测性按 RED 监控请求 Rate、Errors、Duration，按 USE 监控资源 Utilization、Saturation、Errors。至少要有 HTTP P50/P95/P99、JVM/GC、线程池队列、连接池等待、SQL、Redis、MQ lag、Outbox age、AI 成功率/耗时/费用、WebSocket 在线数。

日志使用结构化字段关联 traceId、userId、taskId、eventId、messageId，但不记录 JWT、密码、完整敏感输入和签名 URL。操作日志 AOP 当前只打印且 operator 固定为 admin，应从真实身份读取并可靠落库或进入日志平台。

# 第二部分：30 道生产场景题参考答案

## 场景 1：访问量增长 10 倍

我不会先给出“加机器”的结论，而是先确认各接口 QPS、并发数、P95/P99、错误率、CPU、线程池、连接池、SQL、缓存命中率、MQ lag 和外部 AI 延迟，找到当前瓶颈。容量近似由“吞吐 × 平均响应时间”决定，同一 QPS 下响应越慢，占用中的并发资源越多。

短期止血可以是：对 AI、导出、上传等昂贵接口限流；缓存恋爱记录首页和系统字典；将统计、通知等派生工作异步化；对非核心功能降级；增加无状态业务实例。扩实例时要同时检查总数据库连接数，例如 20 个实例 × 每实例 50 连接已经是 1000，可能先把 MySQL 打死。

分层优化包括：

- Gateway 设置连接、响应超时和用户/IP 限流。
- Web 服务根据 CPU/阻塞比例调整线程，不盲目增大。
- MySQL 优化慢 SQL、索引和游标分页，必要时读写分离或分区，但先解决单库效率。
- Redis 使用批量操作、多级缓存、热点治理和高可用。
- MQ 做削峰，但入口速度不能长期高于消费速度。
- AI 按供应商配额做全局并发和排队，不能跟随业务实例线性放大。
- 静态/图片内容使用 OSS + CDN。

最后用与生产数据分布相近的分阶段压测验证吞吐、P99、错误率和资源饱和点，并留 30%～50% 容量余量。优化成功的标准是 SLO 下可持续稳定运行，而不只是某次压测峰值更高。

## 场景 2：业务服务挂掉

服务进程退出时，Nacos 和健康检查应把实例摘除，Gateway 只转发给健康实例。客户端请求必须有明确超时，避免连接长期占用。GET 等幂等请求可在连接失败、尚未发送或明确可重试错误下有限重试，并带指数退避；创建/修改请求只有具备幂等键时才能安全重试。

如果所有 love 实例都不可用，应快速返回结构化 503 和可重试提示，而不是让请求堆积拖垮 Gateway。其他服务保持可用，说明微服务隔离起效。可使用熔断器在错误率/慢调用超过阈值后暂时停止访问，半开探测恢复。降级可返回只读缓存，但不能把过期数据伪装成强一致结果。

要区分 liveness 和 readiness：进程存活不代表能接流量。线程池耗尽、数据库连接池拿不到连接时，简单 `/actuator/health` 可能仍显示 UP。应增加依赖探针、线程池饱和、事件循环延迟和关键轻量业务探针，并在 readiness 失败时摘流量。

恢复后检查失败期间的写请求、Outbox 积压、MQ 消费、定时补偿和数据对账。OOM 还要保留 heap dump、GC 日志和容器事件，先找根因再单纯扩内存。

## 场景 3：Nacos 不可用

已有实例通常持有本地服务列表和配置快照，短时可能继续互调；但服务上下线信息不能及时更新，旧地址可能持续被调用。新实例可能无法获取配置或注册，扩容和故障替换受阻。是否能启动取决于配置是否 optional、客户端本地快照以及必需配置是否有安全默认值。

生产应将 Nacos 部署为奇数节点集群、独立数据库、跨故障域，并监控注册、推送和配置读取。客户端需要合理超时和缓存，调用端仍必须有超时、重试和熔断，不能把注册中心高可用等同于下游永不失败。

配置发布要有版本、审批、差异、灰度和快速回滚。数据库密码、JWT 密钥等不应只依赖普通 Nacos 明文权限，最好使用 Vault/KMS/云密钥服务，Nacos 存引用或密文，并实施最小权限和审计。

动态刷新并不意味着所有 Bean 可无损更新。线程池大小、连接池、消费者并发等可能需要专门的动态调整 API 或重建资源；更新前后要验证，不支持动态变更的配置应通过滚动发布生效。

## 场景 4：Redis 鉴权故障

首先给 Redis 命令设置很短的超时，并对超时率告警，避免每个请求拖到 Gateway 总超时。高风险写接口、管理接口和隐私数据默认 fail-closed，因为无法确认 Token 是否已被吊销。对于业务明确允许的低风险公开/只读内容，可以单独设计降级，不能全局放开。

高可用层面部署 Redis Sentinel/Cluster 或云高可用版，客户端正确配置拓扑刷新和连接池。网关可对“有效 Token”做几秒到几十秒的本地缓存，减少每请求两次 Redis 查询，但缓存期间被踢出的用户仍可访问，所以 TTL 必须由风险容忍度决定；管理员 Token 可完全不缓存。

还可把 access token 生命周期缩短，使 Redis 长故障时风险上限更小。若使用本地撤销事件广播，要考虑事件丢失，最终仍以 Redis/会话存储为准。

恢复后观察白/黑名单命中、缓存一致性和失败期间的访问审计。不能简单改成只验 JWT 后永久放行，否则项目原本的踢人和注销语义消失。

## 场景 5：MySQL 主库切换

连接异常时存在三种情况：事务尚未提交，可以安全回滚；服务端已提交但客户端未收到响应，结果未知；已经提交并返回后连接再断开。应用不能仅凭异常断言“数据库没有写入”，盲目重试写操作可能重复执行。

正确基础是幂等：创建 AI 任务依赖 userId + clientRequestId 唯一键，状态迁移依赖 version CAS，消息结果依赖 taskId 唯一约束。重试前先按业务键查询结果；仍未知时安全地重放同一幂等请求，而不是生成新 key。

数据源/代理负责发现新主库，连接池要丢弃坏连接并建立新连接，应用设置合理获取连接和事务超时。切换演练要测实际恢复时间，而不是只相信数据库 SLA。

主从延迟下，刚写主库立即从从库查询可能返回不存在，引发错误重试。提交后的关键状态、幂等回查和权限判断必须读主，或使用读己之写策略、GTID 等待；报表和历史列表才适合容忍延迟地读从。

## 场景 6：恋爱记录慢查询

先从接口 P99 和 trace 定位时间是在网关、连接池等待、SQL 还是序列化。检查线程 dump 是否大量等待 Hikari，查看连接池 active/pending；再在 MySQL 慢日志找到具体 SQL，用 EXPLAIN ANALYZE 看扫描行数、索引、排序、临时表和实际耗时。

时间线应使用匹配 coupleId、deleted 和排序键的组合索引，并改为 `(recordDate, sort, id)` 游标分页，避免深 offset。标题包含搜索 `LIKE '%x%'` 无法有效使用普通索引，数据大后拆到全文索引/搜索引擎，或限制为前缀搜索。

还要限制 page size、查询日期范围，避免一次返回全部记录。读取详情和关联图片应批量查询，防止 N+1。只有确认热点且允许短暂不一致后再加缓存，不能用 Redis 掩盖错误 SQL。

创建组合索引会增加磁盘、Buffer Pool 压力和每次 INSERT/UPDATE 成本。大表应使用 MySQL Online DDL 或 gh-ost/pt-online-schema-change，先在影子/从库评估，低峰执行并监控主从延迟、元数据锁和磁盘空间，准备中止方案。

## 场景 7：Hot Key

通过 Redis slowlog、hotkeys、代理统计、应用指标和采样日志识别热点。增加 Cluster 分片未必有效，因为单个 key 只落到一个分片，热点仍受单节点 CPU/网络限制。

图片内容优先放 CDN，应用只提供短期签名或鉴权；系统字典、轮播元数据可做本地 Caffeine 缓存，让每实例承担一部分读流量。对于可拆数据，可按业务维度拆 key 或预计算多个只读副本；热点重建使用 singleflight，避免一个实例内并发回源。

多级缓存一致性通常接受明确的短窗口：数据库更新后提交失效事件，各实例删除本地缓存，同时删除 Redis；事件丢失由短 TTL 兜底。强一致需求不适合随意加本地缓存。

还要防止热点用户执行高成本动态查询：按用户/资源限流、缓存分页首页、预聚合统计，并观察流量是否恶意。优化后看源站 QPS、Redis 单 key QPS、缓存命中率和 P99 是否改善。

## 场景 8：穿透、击穿和雪崩

不存在的 imageId 持续绕过缓存访问 DB 是穿透；一个热门 key 过期时大量并发回源是击穿；大量 key 同时过期或 Redis 整体丢失导致大面积回源是雪崩。

组合治理如下：

- 穿透：参数范围和用户权限校验、短 TTL 空值缓存、布隆过滤器、恶意来源限流。
- 击穿：互斥锁/singleflight 只允许一个请求重建，其他等待或返回旧值；也可使用逻辑过期后台刷新。
- 雪崩：TTL 随机抖动、分批预热、多级缓存、Redis 高可用、数据库限流和降级。

布隆过滤器可能把不存在元素误判为存在，但正常实现不会把已加入元素判断为不存在；误判只会多一次 DB 查询。新增数据必须同步加入过滤器，删除通常不删除位；数据变更大时定期重建，或使用计数布隆但成本更高。

恢复 Redis 时不能让所有请求直接并发回填，应按热点分批预热，并用数据库熔断和限流控制最大回源量。

## 场景 9：AI P99 变成 3 分钟

先拆分 queue wait、claim、模型 connect、首 token、完整响应、结果落库各阶段耗时，判断是排队还是上游慢。为调用设置连接超时、读取/总 deadline，并把剩余预算向下游传播；超过业务允许时间就取消或标记超时，不能无限等待。

模型调用要使用隔离的连接池/线程池和集群总并发限制。当慢调用率超过阈值时熔断或降低新任务接收速度，保护已有任务。租约需大于合理的最大执行时间，并持续续租；不同模型/任务复杂度可使用不同租约和 deadline，但不能把租约简单调到无限长。

客户端展示“排队中”和“处理中”的不同状态，轮询使用退避；系统可以给出预计等待时间。对低价值功能可降级到较小模型、缓存结果或提示稍后重试。

请求超时不代表上游没有完成或计费。若上游支持幂等 key、任务查询或异步 API，应使用 taskId 幂等并先查询结果；否则减少自动重试、记录调用 requestId、人工核对费用。熔断的目标是阻止故障放大，不是让所有任务立即失败。

## 场景 10：RocketMQ 故障与百万 Outbox 积压

先按积压水位和最老事件年龄设置分级策略。短时 MQ 故障可继续接收，让 Outbox 缓冲；当行数、磁盘或用户等待时间超过阈值，应降低 AI 提交速率甚至返回 503/429，避免数据库被无限 Outbox 填满。非核心完成通知可晚些发送，但任务派发直接决定执行，应优先恢复。

监控至少包括 NEW/RETRY_WAIT/SENDING/DEAD 数量、oldest age、发送成功率、发送耗时、数据库扫描耗时、Broker 状态和任务 PENDING 年龄。Outbox 索引必须支持按 status + nextRetryTime 扫描。

恢复后不能一次把一百万条全推给 MQ。Publisher 按批次和速率发送，Consumer 总并发受数据库、AI 配额和模型成本限制；可以先恢复高优先级/较老任务，并逐步提高速率。重试加 jitter，防止所有 nextRetryTime 集中。

单纯提高 batchSize 会增加单轮占用、内存、数据库热点、Broker 突发和 AI 下游压力，还可能让调度线程运行时间超过 fixedDelay 预期。应以端到端可持续吞吐为目标。

## 场景 11：发送成功但未标 SENT

这是 At-Least-Once 的经典不确定窗口。Broker 已经持久化消息，但进程在 `markOutboxSent` 前崩溃；SENDING 超时后被重置并再次发送。不能为了避免重复就直接把超时记录标 SENT，因为第一次也可能根本没发送成功，那会造成消息丢失。

Consumer 必须按业务 key 幂等：AI 使用 taskId 状态 CAS；通用事件可建立 `consumed_event(event_id, consumer)` 唯一表，并将“记录已消费”和业务写入放同一事务；结果表还可对 taskId 建唯一索引。

brokerMessageId 是一次物理投递 ID，重发可能产生不同 ID，不能代表业务事件。应使用 Producer 生成且重试保持不变的 eventId 或 aggregateId。

MQ 事务消息可把本地事务与发送确认协调得更紧，但仍可能重复投递，Consumer 幂等不能省。项目已有 Outbox，除非吞吐/延迟或运维原因充分，不一定需要同时引入另一套事务消息机制。

## 场景 12：模型完成后 Worker 宕机

外部模型调用已经产生，MySQL 事务无法回滚它。新 Worker 只看到任务未成功，会再次调用并可能重复计费。这个问题无法仅靠数据库锁解决。

首选方案是向上游传稳定的 idempotency key，例如 taskId；若上游是异步任务 API，则先持久化 providerRequestId，重试时查询同一上游任务而不是重新创建。也可把执行拆成“已发起—已获得 provider ID—已取结果—已落库”多个持久化步骤，每一步 CAS 推进。

如果上游完全不支持幂等或查询，只能做工程权衡：把租约设为高于合理 P99 并续租，降低非必要自动重试次数，在不确定错误时延迟更久，缓存相同输入的结果，对重复费用告警和对账。不能宣称完全消除重复。

答案的重点是承认本地 Exactly Once 边界，并用业务成本决定复杂度。重复一次几分钱与重复一次高价值交易所需方案不同。

## 场景 13：STW 导致租约接管

旧 Worker claim 时获得 version=V、worker=A；租约过期后新 Worker 抢占，版本变为 V+1、worker=B。旧 Worker 恢复后用 A/V 提交，SQL 条件不匹配，更新 0 行，整个结果事务应回滚，因此不会覆盖 B 的结果。这就是 fencing。

要监控 GC pause、Full GC 次数、堆/老年代、分配速率、线程调度延迟、续租耗时和 renew failure。单线程续租器可因为某次数据库慢查询拖延其他任务，应改为有界 ScheduledThreadPool、批量续租或按任务分片，同时确保线程数不会无上限。

还应在 AI HTTP 调用层支持取消：发现续租连续失败或所有权丢失时尽量取消上游请求，减少重复费用；最终正确性仍靠 CAS，不能依赖取消一定成功。

Redis 锁也有相同问题：锁到期后新客户端获得锁，旧客户端不会自动停止。没有 fencing 的共享资源写入仍可能被旧客户端破坏。

## 场景 14：消息 Schema 不兼容

消息演进遵循“先让 Consumer 能读新旧格式，再让 Producer 写新格式”。新增可选字段并提供默认值通常向后兼容；删除字段、改变类型或改变同名字段语义是不兼容变更，应提升 schemaVersion、使用新 Tag/Topic 或并行 Consumer。

发布步骤可以是：上线兼容 Consumer → 契约测试验证旧样本和新样本 → 灰度 Producer → 观察解析失败和 DLQ → 全量 → 最后在足够长窗口后删除旧兼容代码。回滚时旧 Producer 仍能被新 Consumer 读取。

不可解析消息保留原始 payload、header、messageId、schemaVersion、错误栈和首次时间进入 DLQ。修复 Consumer 后通过受控工具重放到专用重放 Topic，保持业务 eventId 不变以便幂等。

直接改变同一字段含义最危险，因为反序列化仍可能成功，但业务会静默误解数据。Schema Registry 或 JSON Schema/Avro/Protobuf 加契约测试可以更早阻止这种变更。

## 场景 15：MQ lag 上升但 CPU 很低

低 CPU 说明 Consumer 很可能在等待 I/O 或被并发门控。先看消息分区/队列数、活跃 Consumer 数、本地 Semaphore 等待、模型请求并发与耗时、数据库连接池等待、claim SQL 和网络连接池。用每阶段计时确定真正瓶颈。

如果 AI 平均一次 10 秒、全局只允许 8 并发，理论吞吐上限约 0.8 次/秒，增加 CPU 或普通线程没有意义。若分区只有 4 个，增加到 20 个 Consumer 也可能只有 4 个能并行消费。若数据库 claim 慢，则先修索引和连接池。

安全扩容要求同时确认 Broker 分区并行度、上游 AI 配额、DB 写能力和成本预算。可以增加分区、实例和本地并发，但逐步提升并观察错误率与延迟；拿不到许可的消息不要高速失败重投，应减少拉取或延迟重试。

最终用“生产速率、消费速率、lag、最老消息年龄”判断能否追平。消费速率只略高于生产速率时，百万积压可能仍需很久，应计算预计清空时间。

## 场景 16：RabbitMQ 消息进入死信

先根据异常分类：连接/数据库超时属于暂时错误，应重试；记录不存在、格式错误可能是永久错误，不应反复重试。当前第一次失败就 NACK 且不 requeue，会立即进入 DLQ。可增加 5 秒、30 秒、5 分钟等带 TTL 的重试队列，每次失败写 retry-count 和 last-error，过期后由死信路由回主队列；超过上限进入最终 DLQ。

Consumer 更新图片状态必须幂等。若状态已经 SUCCESS，重复消息应直接 ACK；若是合法 PROCESSING 才更新；若记录已被业务删除，应记录原因并决定 ACK/审计，而不是无限重试。

DLQ Consumer 也不能“无论如何都 ACK”。若它将记录标 FAILED 时数据库仍不可用，ACK 会永久丢失补偿机会。可让 DLQ 消息保留、再次 NACK 到专门停车场队列，或先将处理结果持久化到可靠的人工工单表后再 ACK。

运维页面应能查询消息原文、失败次数、异常、关联 imageId/objectKey，并支持权限控制下的单条/批量重放。重放前先确认代码或依赖已修复，否则只会再次制造失败风暴。

## 场景 17：OSS 成功但 MQ 失败

仅在 Producer Confirm 回调打印日志不够，因为进程重启后没有可靠重试依据。应把“对象上传成功、待更新图片状态的事件”持久化为文件 Outbox，或在 image 表记录 OSS_UPLOADED 状态和待通知标记。Publisher 可不断重发，直到 Confirm 和路由成功。

补发前使用 OSS HEAD Object 检查 objectKey 是否存在，并校验 size、ETag/自有 SHA-256、contentType；对象不存在则把记录转 FAILED 或重新上传。消息携带稳定 eventId/imageId，Consumer 用状态条件更新，重复消息不会把终态倒退。

还要监控 PROCESSING/OSS_UPLOADED 的最老年龄，定时扫描超时记录。成功标记与 Outbox 写入应在一个数据库事务中，不能在回调里只做内存动作。

若 Producer Confirm 成功但应用未记录成功，仍会重复发送，所以目标不是绝对不重，而是确保不丢并让重复无害。

## 场景 18：DB 有记录但 OSS 一直失败

为上传定义 CREATED/PROCESSING/UPLOADING/SUCCESS/FAILED 等有限状态，并保存 attemptCount、nextRetryTime、lastError、tempPath 和更新时间。短暂错误有限重试，达到上限转 FAILED，客户端可用同一个 uploadId 重试或重新创建，不能让记录无限 PROCESSING。

临时文件必须有独立目录、大小配额、磁盘高水位告警和定时清理。清理只处理超过保留期且没有活跃任务引用的文件，避免与上传线程竞争。异步任务拒绝或进程重启也要能通过数据库状态重新调度。

清理数据库孤儿时当前逻辑先条件删除 DB，再删 OSS。优点是业务不会再引用对象；缺点是 OSS 删除失败后失去主表追踪，留下对象孤儿，因此应额外写 cleanup_record/Outbox 再异步删 OSS。反过来先删 OSS，如果 DB 条件删除因并发关联失败，会留下有效 DB 记录指向不存在对象，更危险。

更安全的是先通过带条件的事务“标记待删除 + 写删除 Outbox”，异步幂等删除 OSS，成功后物理删除/归档 DB；双向扫描用延迟窗口兜底。

## 场景 19：大文件耗尽资源

入口先限制单文件/单用户大小、并发上传数、每日配额、请求速率和总临时磁盘。Servlet multipart 配置、反向代理和 Gateway 都应有一致上限；临时目录使用独立磁盘或 volume，设置高水位后停止接收，而不是占满系统盘。

GB 级文件不应经业务服务中转。服务端创建 upload session，向客户端发最小权限、短 TTL 的 STS 或预签名分片地址；客户端直传 OSS，完成后提交 uploadId 和 part 清单，服务端 HEAD/Complete 校验后确认。这样业务服务不承担文件字节流，只管理权限和元数据。

真正可恢复的断点续传要持久化 objectKey、uploadId、partNumber、ETag、size、用户、过期时间和状态。当前实现的 uploadId 只在方法局部变量中，进程重启后无法恢复，所以只是单次请求内的分片上传，不是完整的断点续传。

还应校验 MIME 与文件魔数、病毒扫描、文件名规范，并定期 Abort 过期 multipart upload，避免 OSS 保留未完成分片产生费用。

## 场景 20：10 万 WebSocket 连接

容量规划要测每连接 Channel/Pipeline/SSL buffer 的内存、心跳包大小和频率、文件描述符、网卡带宽与 EventLoop 延迟。例如每连接 20 KB，10 万连接仅连接对象就约 2 GB，还不含堆、直接内存和业务缓存。操作系统需调整 fd、backlog、TCP keepalive 等，并通过实际长连接压测验证。

连接建立后在 Redis/一致性存储注册 `userId:deviceId → nodeId`，带心跳 TTL；节点本地保存 nodeId 对应 Channel。业务消息先查路由，再投递到目标节点专属 Topic/队列，或通过内部 RPC 转发。不要向所有节点广播每条私人消息。

粘性会话能让重连尽量回原节点，但节点故障时仍会改变，不能作为唯一正确性基础。Redis Pub/Sub 简单但离线不持久；MQ 可持久化并支持重试，但节点队列生命周期和路由更复杂。关键通知应先持久化，再尝试在线推送。

优雅下线时先停止接新连接、从路由摘除、通知客户端重连，等待或转移待发消息，然后关闭 EventLoop。EventLoop 中绝不执行数据库或慢业务逻辑。

## 场景 21：在线判断与消息交付竞态

“Channel 存在”只表示判断瞬间在线，不表示消息已经送达。应先给通知分配 messageId 并持久化为待投递，再尝试在线发送。Channel write 成功只表示写入本地缓冲或内核，不代表客户端收到；若业务要求可靠，客户端收到后要 ACK，服务端再将消息标为 DELIVERED。已读是更高层状态，通常由用户行为单独上报。

节点宕机后，未 ACK 消息通过超时扫描重新投递或在用户重连时拉取离线消息。重复推送不可避免，客户端按 messageId 去重，服务端更新状态也要 CAS。可以设置最大重试和过期时间，避免永久消息。

多设备场景要先定义语义：普通通知可任一活跃设备 ACK 即视为已送达用户；安全通知可能要求每设备单独状态；聊天消息还要区分已送达和已读。模型应记录 deviceId 或维护 delivery 明细，而不是一个全局 boolean。

关键是把“在线优化”与“可靠事实”分开：Channel 推送降低延迟，持久化状态确保可恢复。

## 场景 22：并发创建情侣关系

“先 count 再 insert”不是原子操作。在 READ COMMITTED 下两个事务都能读到 0 并插入；即使 SERIALIZABLE 能阻止，也会降低并发并增加死锁，不是首选。

将双方 ID 规范化为 `user_low=min(A,B)`、`user_high=max(A,B)`，建立唯一键 `(user_low,user_high,active)` 或维护独立 active relationship 表。若业务规定一个用户同一时间只能有一个伴侣，还要保证每个 user 只能出现在一个有效关系中，这可能需要两行 membership 表，对 userId 建唯一约束，并在同一事务写入。

应用可以先查提供友好提示，但真正兜底是数据库唯一约束。并发冲突捕获 DuplicateKeyException，回查现有关系后返回 409。分布式锁只能减少冲突，锁失效、过期和绕过时仍需数据库约束。

owner=A/partner=B 与 owner=B/partner=A 通过规范化 pair key 变成同一组合，避免方向不同绕过唯一性。

## 场景 23：伪造 userId 越权

第一步网络隔离业务服务，攻击者不能直接访问；第二步业务服务仍验证 JWT 或网关内部凭证；第三步 Controller 从 `CurrentUser` 获取身份，忽略 DTO 中的 ownerUserId/creatorUserId；第四步 Mapper 把归属条件放入 SQL。

例如查询 love record 不应只写 `WHERE id=?`，而应 join/exists `love_couple`，要求当前 userId 是 owner 或 partner 且关系有效。UPDATE/DELETE 同样把归属写进 WHERE，并检查影响行数。这样即使 Service 层遗漏检查，SQL 仍不会修改他人资源。

只在 Controller 先查归属再更新可能有 TOCTOU，也可能被其他调用入口绕过；Service 授权和 SQL 约束应配合。不存在和无权限可统一返回 404，降低资源枚举。

管理员通过统一 Policy/AuthorizationService 判断，并记录操作人、目标用户、理由和结果。不能让 admin 角色直接绕过所有审计。

## 场景 24：refresh token 并发与盗用

使用 Lua 原子执行：读取 refresh jti 状态，确认 ACTIVE；将其改为 USED/删除白名单；记录新 jti 或返回一次性授权。只有第一个请求成功，第二个看到 USED 即判定重放。单纯 `hasKey` 后 `delete` 是两步，不能防并发。

每次登录会话建立 token family，记录 familyId、deviceId、当前 refresh jti 和版本。正常刷新只吊销旧 jti 并推进版本；若已经使用过的旧 Token 再出现，说明可能被盗，可以吊销整个 family 并要求该设备重登。高风险系统还可吊销用户全部 family，并通知用户。

多端登录时每个设备是独立 family，这样一个设备泄露不会必然踢掉所有设备。Redis key TTL 与 refresh 最大寿命一致，审计记录可保留更久。刷新接口也应限流、检查客户端/设备特征，并通过 HTTPS 和安全存储保护 Token。

## 场景 25：主键冲突与时钟回拨

当前生成器没有机器位，多实例同毫秒同 sequence 会碰撞；时钟小于 lastTimestamp 时直接抛异常。短期可停用多实例写入或为每实例配置唯一 workerId，使用成熟 Snowflake 库，并监控 NTP 偏移。若无法可靠分配 workerId，号段服务通常更稳妥。

长期可引入数据库号段/Leaf，实例一次获取一段 ID 在内存发放，数据库不可用时仍可使用未耗尽号段；或使用云 ID 服务。迁移时 BIGINT 类型不变，新旧生成器可共存，只要 ID 空间不会重叠。前端统一字符串传输，避免 53 位精度问题。

时钟回拨可在小范围等待到 lastTimestamp、使用逻辑时钟/备用 workerId，较大回拨直接摘除实例并告警，不能默默产生重复。机器时钟本身用 NTP chrony 渐进校准。

主键 DuplicateKey 不一定来自幂等联合键。捕获异常后必须按 userId + clientRequestId 回查；查不到说明可能是 ID 主键冲突，应重新生成或报警，不能错误返回“请求已提交”。

## 场景 26：不停机改表和消息

使用 Expand–Migrate–Contract：

1. Expand：先增加可空列或有兼容默认值，旧代码完全不受影响；新 Consumer 先支持新旧消息。
2. Deploy：新代码双写新旧字段或写新字段、读取时先新后旧；新 Producer 灰度发送新增字段。
3. Migrate：后台按主键小批回填，记录进度，可重复执行；监控锁、IO、主从延迟。
4. Enforce：确认全部数据和实例迁移后，再加 NOT NULL/唯一约束。
5. Contract：经过一个完整回滚窗口后停止读写旧字段，最后删除。

消息遵循先 Consumer 后 Producer，因为新 Consumer 可兼容旧消息，旧 Consumer 未必能读新消息。不可兼容变更使用新版本 Topic/Tag 并行迁移。

大表回填用 `WHERE id > lastId ORDER BY id LIMIT n` 分批提交，动态降速，失败从 checkpoint 继续；避免一次大 UPDATE 产生长事务、undo 和主从延迟。数据库迁移必须与应用回滚兼容，必要时选择前滚修复而不是回滚 schema。

## 场景 27：多实例定时任务重复

不是所有重复执行都要全局锁。AI Outbox Publisher 可以所有实例同时扫描，因为每行通过 version CAS 只有一个实例 claim；超时恢复也通过任务状态/version 条件更新，适合并行。清理 SENT 若 SQL 条件删除且分批，重复执行通常也是幂等的。

无法自然分行抢占的全局汇总、外部通知或文件扫描，可使用 XXL-JOB 分片、数据库租约/leader election。Redis 锁必须有 owner token、续租和安全释放，且外部写入最好带 fencing；任务时长超过锁 TTL 时会双执行。

分布式锁只减少同时执行概率，不能代替业务幂等。网络分区、锁服务故障、进程暂停都可能让两个执行者存在。最终写操作仍应有唯一键、状态 CAS 或幂等 eventId。

任务需要记录 runId、开始/结束、扫描范围、影响行数和错误，支持从 checkpoint 续跑，并对长时间未完成、重复抢占和积压告警。

## 场景 28：机房故障与灾备

先把业务要求转成方案：RPO 5 分钟表示最多可丢 5 分钟数据，RTO 30 分钟表示 30 分钟内恢复核心服务。MySQL 需要定期全量备份 + 持续 binlog 异地保存，并演练 PITR；Redis 若只作缓存可重建，若承载会话/限流则需 AOF、跨可用区副本并接受部分会话丢失的影响；MQ 使用多副本和异地备份/镜像策略；OSS 开启版本控制和跨区域复制。

恢复顺序一般是身份与配置依赖、数据库、Redis、MQ、业务服务和后台任务。先限制入口，恢复数据库到选定时间点，再恢复 Broker offset/消息，启动 Consumer 前检查状态，最后逐步放流量。

MySQL 到 T1、MQ 到更晚的 T2 可能让消息引用数据库中不存在的业务记录；MQ 更早则可能缺少已提交业务的事件。Outbox 能从数据库事实重新发送未确认事件，Consumer 对不存在资源要延迟/死信而非破坏数据；上线后通过任务状态、Outbox、OSS 引用等对账修复。

备份不等于可恢复，必须定期在隔离环境演练，记录实际 RPO/RTO、密钥和配置恢复、DNS/流量切换以及回切方案。

## 场景 29：P99 延迟升高

平均值正常不能否定长尾。先从 Gateway 的路由级 P50/P95/P99、状态码和 in-flight 请求找受影响接口，再沿 trace 查看 DNS/连接、业务线程等待、Redis、SQL、MQ 或外部调用 span。没有 trace 时用同一 traceId 串联结构化日志。

同时查看 JVM GC pause、堆和直接内存、CPU throttling、线程池 active/queue/reject、Tomcat busy threads、Hikari pending/timeout、MySQL 慢查询/锁等待、Redis 延迟、MQ lag、外部 AI 分位数。线程 dump 可识别大量 BLOCKED、连接池等待或 EventLoop 被阻塞；必要时用 async-profiler/JFR。

短期按证据采取摘除异常实例、回滚、限流、关闭慢功能、扩容或熔断，而不是同时修改所有参数。修复后对比同一时段的 P99、饱和度和错误率。

日志采用概率采样，但错误、超时和慢请求 100% 保留；trace 可用 tail-based sampling。SLI 例如“30 天内 99.9% 请求小于 500 ms 且成功”，告警使用错误预算 burn rate，减少静态阈值造成的噪声。

## 场景 30：发布失败与回滚

流水线应包含编译、单元/集成测试、Mapper 与消息契约测试、安全/依赖扫描、数据库迁移校验、镜像构建和签名。制品一旦生成不可修改，同一镜像从测试晋级到生产。先部署少量金丝雀实例，只接小比例流量，以错误率、P99、资源、MQ/Outbox 等指标作自动门禁。

高风险功能使用 Feature Flag，可在不回滚整个版本时关闭。应用回滚要求新数据库结构和新数据仍能被旧版本读取，因此迁移必须遵循 expand-contract。若新版本已发出旧 Consumer 不认识的消息，单纯回滚 Jar 可能继续消费失败；若已执行删除列等破坏性 DDL，也无法直接恢复旧代码。

因此发布前做双向兼容测试：新版本读取旧数据/消息，旧版本读取新版本写入的数据/兼容消息。数据库只做向前兼容扩展，破坏性收缩延迟到回滚窗口之后。故障时优先关开关、停止新流量，再根据数据变化选择回滚应用或前滚修复。

发布完成后保留变更记录、迁移版本、指标对比和复盘；“一键回滚”必须包含应用、配置、流量和消息消费策略，而不是只切换镜像标签。
